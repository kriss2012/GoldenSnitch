Golden Snitch — Final Product Build Roadmap

Purpose

This document pack is the execution plan for turning the existing Golden Snitch repository into a coherent full-stack esports scouting and multi-roster intelligence product. It is written for implementation by a coding agent or development team. The instructions require inspecting the current repository before changing it; the architecture below is a target, not an assertion that all listed components already exist.

Product outcome

A user can register or sign in, access only authorized workspace data, scout candidates for a game and role, understand each recommendation's evidence and confidence, compare candidates, manage multiple rosters, simulate recruitment impact, maintain a scouting pipeline, receive persistent in-app notifications, export reports, and sign out securely.

Design authority

Target architecture

Confirm actual repository choices before adopting these defaults:

Frontend: React + Vite + TypeScript + Tailwind CSS + React Router.

Data visualization: Recharts.

Icons: Lucide React.

Backend: Python 3.12 + FastAPI + Pydantic.

Persistence: SQLAlchemy and SQLite for local MVP; preserve an existing supported database if already integrated.

Tests: pytest for backend; Vitest/React Testing Library for frontend; Playwright for end-to-end and responsive checks where feasible.

Auth: preferably opaque server-managed sessions in HttpOnly cookies, with CSRF protection for cookie-authenticated mutations. Use an alternative only if the current architecture justifies it.

Local development configuration through environment variables.

Build principles

Inspect first; do not overwrite functioning code.

Migrate the existing database safely; never delete user data to make a migration pass.

Backend is the source of truth for private data, authorization, notifications, and persisted product records.

Do not claim live AI, live esports API data, email delivery, or push notifications unless implemented and verified.

Keep simulated datasets clearly labeled.

Separate UI components from domain logic and API calls.

Each phase must pass its exit gate before the next phase is treated as complete.

Record commands actually run and test outcomes honestly.

Definition of done

A feature is not complete merely because it renders. It must:

Have a defined user story and acceptance criteria.

Validate input on the backend.

Enforce authentication and permissions where applicable.

Persist data where persistence is required.

Display loading, empty, success, and failure states.

Be usable with keyboard and touch.

Be tested at relevant levels.

Have documented limitations and setup requirements.

Critical end-to-end acceptance journey

User registers with a valid email and password.

User signs in and the frontend retrieves the authenticated profile from the backend.

User opens a vacancy and ranks role-compatible players.

The result includes score components, confidence, sample size, and evidence-based explanation.

User shortlists a candidate or performs a roster action.

Backend commits the operation and creates a relevant notification only after success.

Notification appears with the correct unread count.

User marks it read; the change persists after refresh.

User signs out.

The revoked session cannot access protected frontend routes or private APIs.

A different user cannot access the first user's private records by changing IDs.

Release gate

Do not label the product final until the build passes, core flows are verified against the real backend, database migrations work on a clean and existing database, and known gaps are documented.

The project has previously reported that the virtual environment's Python could not import pip. Verify before changing it:

Goal

`POST /api/v1/auth/forgot-password`

`POST /api/v1/auth/reset-password`

Session refresh/revocation endpoints only if required by the selected architecture.

Security implementation

Prefer opaque, random server-managed sessions in `HttpOnly` cookies for a browser application, unless the existing architecture justifies another design. Configure `Secure` in HTTPS production, an appropriate `SameSite` policy, expiry, narrow scope, and CSRF protections for state-changing cookie-authenticated requests.

Use a reputable password hashing library and modern password hashing such as Argon2id. Never store plaintext passwords or reversible password encryption.

Implement:

Normalized email handling and duplicate rejection.

Generic invalid-credentials responses.

Login rate limiting.

Session expiry and revocation.

Session rotation after authentication/privilege changes.

Backend role checks and ownership checks.

Safe CORS configuration.

No secrets in source code or logs.

A controlled first-admin bootstrap process.

If JWTs are already used, review token expiry, refresh rotation, revocation, and storage rather than mixing two session systems without a design.

Password reset

Generate cryptographically random, single-use, expiring reset tokens. Store a hash of the token where practical. Never reveal whether an email is registered in public responses. In development, expose a safe local-only method for inspecting reset links; in production, use a configured email provider. Clearly report when email delivery is not configured.

Phase 6 — Scouting Intelligence and Explainable Ranking

Goal

Provide consistent, role-specific, evidence-backed candidate ranking.

Scoring

Use normalized factor scores on a 0–100 scale. Store a scoring formula version with each evaluation. Keep the weights configurable and validate their total.

Illustrative IGL weights:

Mid-round decision quality: 25%

Calling impact: 25%

Team coordination: 20%

Tactical adaptability: 15%

Performance consistency: 10%

Mechanical contribution: 5%

These are demo assumptions, not an industry-standard formula. Provide separate role/game-specific factors. Do not compare raw scores across different games as if they were directly equivalent.

Confidence

Confidence must be separate from Talent Index. Consider sample size, metric completeness, recency, and performance stability. Initial configurable demo thresholds may be fewer than 10 matches = low, 10–29 = medium, 30+ = high. Label these as product assumptions.

Recommendation response

Return:

Candidate identity and game/role.

Overall Talent Index.

Factor values and weights.

Confidence label and reasons.

Valid match count.

Data completeness.

Evidence-based strengths.

Risks and missing data.

Formula version.

Data source label.

Explanation quality

Every explanation must point to a metric or data fact. Do not invent causal claims such as “this IGL will guarantee wins.” If calling impact is observational, state that association does not prove causation.

Synergy simulation

Define the formula and its limitations. Include role coverage, complementary strengths, historical coordination where available, and performance consistency. Label projected scores as simulated estimates, not guaranteed win-rate changes.

Tests

Weight validation and normalization.

Correct role/game formula selection.

Deterministic output for deterministic input.

Insufficient sample-size handling.

Missing metrics.

Sorting and tie behavior.

Confidence separate from score.

Evidence references match the values displayed.

Exit criteria

A manager can choose a game, role, and vacancy, rank candidates, inspect why the candidates rank as they do, and see confidence and sample size without fabricated claims.
